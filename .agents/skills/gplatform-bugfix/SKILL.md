# Bug 修复的判断与实施

所有代码变更先执行下列范围检查点；bug 修复再执行后续完整流程。按涉及的模块读取相关领域技能，具体接口与操作方法以当前代码和领域技能为准。
思考应落实在方案和 diff 中；小修复不要求额外设计文档、逐项汇报或重复审批。

## 修改范围检查点

- **动手前**：结合用户要求和已有工作区差异，简述本次目标、涉及模块和不修改的边界；用户已否定的方案持续有效，未经重新授权不得恢复。先查现有能力，每项拟增行为都须对应当前需求或有证据的必要依赖。
- **实施中**：完成一个工作项就复查该项差异。若发现需要增加未包含在要求或已批准方案中的交互、公共接口、底层机制或全局行为，先说明缺口、必要性和替代方案，待用户确认后再实施。必要的配套修改和普通实现细节在已授权范围内直接完成，不逐文件请求审批。
- **验收边界**：优先通过已有业务接口观察和驱动程序。不能仅为读取 DB、驱动场景或获得通过而增加产品入口、镜像状态或改变业务行为；不得擅自放宽断言或改写既有基准。验证发现真实产品缺陷时，按缺陷所属职责修复并给出依据。
- **交付前**：主动审核完整 diff，区分本次修改与用户已有内容。逐文件核对其必要性及对外行为变化，撤回本次引入的无关改动；有争议的内容明确列出，不能混入“审核通过”。分别报告范围审核、编译和业务验证结论。无需提交逐轮调查日志或另建过程文档。

## 先确认问题和任务目的

- 明确触发条件、实际行为、合理的预期行为，以及本次要恢复或保证的结果。区分产品缺陷、需求变化、配置/依赖不匹配和验证方式错误，依据证据处理。
- 从用户意图、现有契约、相邻功能和真实调用链核对预期；当前实现和旧文档都可能有误。用户提出的实现办法也需评估是否能解决目标问题，不能只按表面症状套补丁。
- 尽量固定最小复现或失败证据，沿输入、状态生成、传播和消费找到首次偏离预期的位置。无法复现时说明已确认的事实与剩余假设，不把推测写成根因。
- 查最接近的正确调用者、已有 helper、同类操作和回归用例，确认能否复用已有机制修正；旧实现不合理时说明缺口，不能为了少改几行复制错误模式或增加平行规则。
- 保留用户已有改动，明确本次修复的行为范围。与目标无关的问题记录后单独处理，不顺手扩展任务。

## 修改前评估四个方面

| 角度 | 必须回答的问题 | 对修复方案的要求 |
| --- | --- | --- |
| 合理性 | 修复后的行为是否符合使用场景和现有契约？是否只消除了症状？ | 保证实际结果正确；保留合理的失败、取消和恢复语义，不以隐藏错误或放松校验制造成功。 |
| 架构 | 哪一层拥有错误状态或规则？方案是否破坏依赖方向、数据来源或生命周期？ | 在合适的职责处修正，沿已有接口传播；需要调整既有设计时说明其缺陷与必要边界。 |
| 复杂度 | 新增的分支、状态、缓存、配置、抽象或重试是否有当前问题证明必要？ | 优先使用已有能力和直接表达；新增机制需有明确所有者、失效/清理方式及失败行为。 |
| 范围 | 每处改动与本次目标有何因果关系？是否混入重构、清理或额外功能？ | 选择最小且完整的修复；必要的上下游配套改动一并完成，无关工作移出本次。 |

代码行数不是唯一标准。局部补丁若留下错误状态、重复规则或另一路径的同一缺陷，就不算完整；跨文件修改若是修复同一因果链所必需，可以保留并说明。
现有架构约定优先核对，其错误也需要修正；不能为了表面上维持旧结构而继续叠加补丁。规模明显超出本次目的的重设计，应先分清本次必要修复与另行演进的内容；真正缺少会改变行为选择的信息时再澄清。

## 独立审核（按需）

用户要求 agent 审核或项目已有明确独立审核要求时，按以下方式执行；普通小修改不因此自动增加 agent、审核文档或审批流程。

1. **先独立定位，再对照方案**：先给审核者原始需求、用户已确认的边界、必要证据和源码入口，使用不含作者候选方案、预期答案和先前结论的上下文。让其从真实调用链判断现有能力和最小完整修改方向，再提供候选方案或 diff 作对照。已接触候选方案的审核只能称作对照审核，不能宣称完成了独立定位。
2. **逐项检查新增机制的必要性**：对新增 DB、状态、接口、抽象或管理器，指出最接近的现有能力，依据源码说明为何不能复用、缺口是什么，以及缺口是否属于当前需求。未证明必要的增量应要求删减或补证，不能默认接受。不能用未经用户要求的统一化或未来场景，否定能够满足当前目标的更小方案；现有实现有缺陷时也不能盲目复用。
3. **明确结论及成立条件**：给出针对具体方案或 diff 的“通过／需调整／阻断”，附关键依据、适用范围、未证实事项和必要条件。仅在扩大目标后成立的设计，应标为超出当前范围，不能转成原任务的必需改动。不为凑审核问题而强行反对已有充分证据的合理实现。
4. **核对最终版本**：将准备实施或交付的方案与被审核版本对照；若对象模型、职责、依赖方向或修改范围发生实质变化，把变化部分交给审核者复核，不沿用旧结论。只复核受影响内容，不机械重做完整审核。
5. **准确转述审核结果**：作者不得把条件性、局部认可或尚待验证的判断概括为整体通过。分别说明方案审核、源码检查和实际验证的结论；agent 认可不能替代需求满足、范围检查或运行证据。

## 在本项目中如何落实

- **UI 与业务分工**：布局、焦点和弹窗局部状态在合适的界面层处理；业务规则沿 DB、Handler/服务和 Bridge 修正。排查属性通知和状态失效，避免在 QML 复制内核规则或使用定时刷新掩盖通知缺陷。
- **DB 与事务**：核对实例/共享对象归属、修改粒度、Undo/Redo 与失败回滚。`TransactionGuard` 析构默认提交，不能假定异常自动撤销；也不能因使用事务就省略生命周期分析。
- **异步与渲染**：区分任务接收、计算完成和结果提交，检查线程、代次、对象保活与取消。任意延迟、轮询、重试或重复信号不能代替对竞态和帧/资源归属的定位；确有协议需要时才增加相应机制。
- **切片与 SDK**：先核对最终输入/参数、库的真实来源及预览消费者。几何与规划错误在所属阶段修复，配置/ABI 不匹配按真实依赖契约解决，不绕过校验或修改最终文本掩盖问题。

这些是判断入口，不要求每个 bug 检查所有模块。按已发现的因果链选择领域技能和验证范围。

## 实施与验证

1. 在拥有问题的层修正，优先复用已有接口和状态。只在当前缺陷需要时增加辅助函数、类型或机制；保持相关代码风格。
2. 检查与同一原因直接相关的调用路径和边界，必要时完成接口、资源、注册或 ABI 配套。不要借机统一不相关实现。
3. 使用能观察真实错误的验证，条件允许时证明修复前失败、修复后通过。优先复用已有用例；对有复发风险的行为增加适度的回归覆盖，不为低影响改动机械新增测试。
4. 根据影响检查正常路径与相关取消、失败、重试、撤销或共享实例等边界，不默认执行无关完整矩阵。UI 输入缺陷要验证对应输入，底层调用成功不能扩大为整条用户流程通过。
5. 复查最终 diff：每个文件是否必要，是否复用正确的已有能力，是否引入双重状态来源或重复规则，是否遗留临时日志、调试开关、无关格式化、未使用分支或被放宽的断言。移除本次引入的无关内容，保留用户既有工作。

修复完成应同时满足：目标行为恢复、架构与状态一致、复杂度有必要、范围可解释，并有与结论匹配的验证证据。测试通过不代替前四项判断；环境受限时明确未验证部分。

## 向用户说明

根据任务复杂度简要说明根因、修改位置及其合理性、实际验证和剩余限制。存在必要的额外机制或跨模块修改时解释原因；无需每次输出完整评估表。
