# DB 与 Action 开发

用于需要改变或追踪业务状态的任务。路径除 `HOST_ROOT` 标记外均相对 `APP_ROOT`。

## 先确定契约与现有能力

先明确目标对象、输入参数、状态前后差异、归属/共享关系、历史粒度、输出和失败语义；已有操作的修复守住当前合理契约，不默认新增 Action 或 DB 类型。
查最接近的 Handler、Bridge、DB 属性与关系、模型操作工具和测试，追踪它们实际怎样修改状态。优先调用已有业务能力，不能把一份 Handler/对象图处理复制到另一层后独立维护。
在已有参数、属性、关系或组合路径内可以表达需求时直接使用；确有缺口再添加最小接口或类型。不要为了单个操作新建平行文档、Undo 栈、对象注册器或额外状态同步层。

## 沿实际执行链定位

```text
QML/正式调用者 → ActionManager 或现有 Bridge/服务
→ Handler/业务操作 → DB setter 与事务
→ DocumentManager/DBRelations → Bridge 或渲染消费者
```

先检查具体入口；ActionManager 不会自动为每个业务操作创建事务。保留现有正常的 Bridge 直接操作路径，不把所有 setter 强行迁移为 Action。

## 按任务读取

- 新 DB、模型图、对象归属、事务与临时对象：[DB 与事务](references/db-and-transactions.md)。
- Handler、异步结果、AI 参数契约、QML/Action 与模块注册：[执行与注册](references/actions-and-registration.md)。

## 修改方法

1. 记录目标对象、所属模型/打印床、操作前状态及预期 Undo/Redo 行为；确认修改的是实例、共享对象、部件还是几何，并检查现有操作是否已经覆盖需求。
2. 找到负责修改的具体 Handler/服务及已有事务范围；一次用户编辑需要什么历史粒度，由行为决定。保留正常的入口分工，不为共享代码把交互或 GUI 状态带入纯业务计算。
3. 复用已存在的属性、关系和注册宏。新增关系同时考虑归属、删除策略、克隆/序列化、失效通知及消费者。
4. 对异步操作分别确认接收、计算、提交、取消和错误终态；异步结果发布前重新确认对象及请求仍有效。
5. 以最终 DB 与相关历史验证修改，必要时检查 Bridge、渲染和用户输入入口；复查新增状态/关系是否必要、是否重复已有规则，及共享操作的直接调用者是否保持正确。

## 必须核对的当前行为

- `AutoRegisterDB::onCreated()` 是 `final`：扩展初始化钩子，不能依照旧注释重新覆盖它。
- `TransactionGuard` 析构默认提交；需要撤销部分写入的失败路径显式 `rollback()`，不能假定异常自动回滚。
- `DocumentManager` 的监听回调在发布通知的调用线程运行；监听容器有锁不代表回调自动进入 GUI 线程。
- `triggerAction()` 的布尔返回及 `accepted` 不等于异步业务完成；检查结果与完成信号。

## 验证

按改动检查对象归属、非目标实例保持不变、Undo/Redo、取消和失败后恢复。完整宿主中可选择对象图、事务关系、模型编辑、临时 DB 或启动注册相关检查；先核对测试名和依赖。
只验证 SDK 接口时说明其范围，不能等同于菜单、快捷键、拖拽链路已经通过。
bug 修复同时应用 `gplatform-bugfix`。交付时简述复用入口、必要增量和实际证据，不为每个属性修改生成额外方案文档。
