# 渲染开发

本技能随 App 保存。App 提供 `src/Base/BaseRender` 中的接口和交互消费者；修改内置后端或 Qt 呈现实现需要可访问的完整源码宿主。缺少私有源码时限定接口级定位，说明需要的实现，不猜测其内部行为。

## 定位链路

```text
业务 DB/关系通知 → IDocumentReadView
→ VTK DBRenderAdapter 或 FilamentSceneAdapter → 后端 DBSync/渲染线程
→ IRendererSession/PresentableFrame → Qt 呈现与帧归还
```

先区分 DB 终态错误、通知遗漏、后端同步、帧呈现、相机或拾取坐标问题。

## 从需求和现有后端开始

1. 明确预期视觉/交互结果、目标后端与视图、输入 DB/资源/坐标、输出帧或拾取结果，以及相关性能约束。
2. 阅读相同角色和最接近的生产实现，确认既有 BackendCatalog、工厂、Session、DBSync、共享转换工具和能力接口能否满足需求。
3. 优先通过既有属性、同步路径和能力实现；只有当前接口确实不能表达时才扩展契约。保留后端私有资源，不为一个显示问题新建整套渲染层或改写 App。
4. 在拥有问题的层做必要增量，先验证该层契约，再按需要检查真实视口与直接受影响的使用处。

不同后端可以有不同内部实现；复用共同语义，不为统一代码形式强行合并其线程、缓存、缓冲池或生命周期。

## 阅读入口

接口、实际后端、帧交换、拾取和相关检查见 [渲染源码与契约](references/rendering-contracts.md)。路径分别以 `APP_ROOT` 和存在时的 `HOST_ROOT` 为基准。

## 修改边界

- 后端通过 BaseRender 的工厂、Session 和能力接口扩展；不要将 VTK/Filament 类型或私有头文件暴露给 App。
- 文档通知可能来自 GUI 或后台线程。VTK 回调先排队，由渲染线程管理 DBSync；不能在回调中直接操作其映射和原生渲染资源。
- 核对角色、view ID、generation、物理尺寸和设备标识，保留多视口、标签切换、resize、暂停和销毁路径。
- `frameReady` 只是通知；权威帧由具体 Session 持有，消费者调用 `tryAcquireReadyFrame()`。保留 acquired、discard、release 和 GPU completion 各自的职责。
- 图形上下文创建成功时由 Session 消费，工厂失败时调用方仍负责释放；shutdown 需要等待相应帧租约与 GPU 完成。
- 拾取沿当前视图能力和请求代次处理，区分逻辑坐标、物理像素和世界/模型局部坐标；不复用已销毁视图的结果。
- 现有调度、失效和帧归还能解决问题时不再增加轮询、全局刷新或第二份场景状态。新增锁、缓存、线程或 GPU 等待需有实际原因，明确所有者与清理方式。
- 公共接口或共享同步逻辑确需修改时检查直接消费者；局部材质/相机/显示问题不默认扩大成全部后端重构。

## 验证

按问题选择接口、帧状态机、后端集成或真实视口场景，确认测试是否需要 OpenGL/GUI 环境。涉及两个后端共享接口时检查两者编译及相关契约。
渲染性能任务固定场景、后端、视口尺寸与统计条件，同时检查结果与交互；不要以单张截图或 offscreen 通过推断真实 GPU 呈现正确。
bug 修复同时应用 `gplatform-bugfix`。完成前检查每项改动是否修复对应阶段、是否复用现有机制，说明新增契约/状态的必要性与实际验证范围。
