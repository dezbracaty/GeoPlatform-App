# 原始能力提取与协议封装

本文件路径相对 `SLICER_ROOT=APP_ROOT/ThirdParty/OrcaSlicer`。目标是使同一能力可以由纯库调用，保留 Orca 已有语义，并控制实现范围。

## 1. 先形成库契约

先从需求定义可独立调用和验证的输入/输出边界。检查 `include/libslicer/Library.hpp`、`Config.hpp`、`Calibration.hpp`、`Toolpath.hpp` 等现有公开定义，优先扩展最接近的能力，不机械新增另一套 Service/Manager/DTO。

按相关性明确以下事项；简单能力只需写清实际涉及部分：

| 契约 | 要明确的内容 |
| --- | --- |
| 能力与调用 | 做什么、调用哪个入口；需要单次操作还是确有必要的 prepare/execute 生命周期 |
| 输入 | 模型/体积/实例、配置快照、参数类型、必填与默认、合法范围、枚举和索引基准 |
| 几何与单位 | 输入/输出坐标系、矩阵布局、长度/角度/速度/流量单位、精度与容差 |
| 输出 | 几何/配置/刀路/文件或任务句柄、统计与诊断；是否含多对象/多盘及其对应关系 |
| 状态与失败 | 成功、警告、拒绝、取消、部分结果的含义；失败后的对象和文件是否保留 |
| 归属与资源 | 输入快照、返回对象/缓冲区/临时文件由谁持有和清理，资源目录如何提供 |
| 执行约束 | 调用线程、并发/重入、进度回调和取消；仅为实际异步需要定义额外状态 |

这里的协议首先是现有 C++ SDK 契约；只有真实跨进程或外部消费需求才增加相应序列化协议。不要将 App DB ID、QObject、窗口、GUI 全局活动预设或可变实时界面状态泄漏为算法所需依赖。
先定义边界再查原始实现；源码发现的必要输入和语义应回填到同一份契约。既有接口上的 bug 修复以澄清和守住该契约为主，不默认更换公共 API 或 schema。

## 2. 确认原始分支与提交

当前 fork 已去掉 wx GUI，原始能力需要从保留 GUI 的历史分支/提交读取。先检查本地 refs、历史与已有来源记录，确认该功能对应的版本；`origin/main` 只是一个 ref，不能不经核实当作指定原版或最新上游。

可在 Orca 仓库只读查询，替换占位符后执行：

```sh
git branch -a
git rev-parse <reference-ref>
git ls-tree -r --name-only <reference-commit> -- src/slic3r/GUI
git show <reference-commit>:src/slic3r/GUI/<file>.cpp
```

记录实际提交、源码路径和函数。直接读取 Git 对象，不切换或覆盖正在开发的工作树。若本地没有所需对象，说明缺失来源后通过可用的正式源取得并记录；无法查证时不宣称与原始实现一致。
对新能力查最接近的原始流程；确无原始实现时说明已查范围与缺口，再实现需求所需的最小增量。

## 3. 从 GUI 追踪完整业务行为

沿“控件事件 → 解析/联动/失焦处理 → 校验/预检 → Plater 等业务入口 → 模型和配置准备 → 内核 → 结果/导出”逐层检查。
不能只看最终算法函数，遗漏 GUI 原本承担的默认值、单位转换、配置覆盖、材料/固件分支、模型资源或多盘行为；也不能把显示逻辑和窗口副作用全部搬进库。

把原始逻辑分成三类：可直接调用的内核/工具；需要去 GUI 依赖后提取的业务代码；由调用端继续负责的界面行为。字段标签可供翻译，数值含义与执行规则在库内保持一致。

## 4. 复用与适配的边界

- 原有内核可满足需求时直接调用；算法位于 GUI 业务层时提取相关实现，尽量保留计算、配置准备和资源处理。
- 以显式请求配置、局部模型/任务上下文替代 GUI 全局访问；对窗口通知映射为诊断或必要回调。可以保留必要的数据操作上下文，避免模拟 wx 应用、主窗口和整套 GUI 对象图。
- 协议封装负责类型转换、调用编排与结果映射，不另外推导同一算法或复制参数规则到 App。复用存在局限时指出具体差异，不增加需求未要求的选项、缓存、重试和插件层。
- 去除 GUI 耦合与改变算法分别审查；不要在一次提取中顺便重排流程、改采样/阈值、扩大容差或更改配置默认值。
- 新文件、公共类型和状态只在现有边界不能清楚承载当前能力时增加；遵守 Orca 子仓库自身的文件和构建约束。

## 5. 当前校准实现的可核对示例

以下示例用于说明提取方式，不要求其他能力复制同一套类或文件布局：

- `include/libslicer/Calibration.hpp`：公开请求、配置快照、表单状态、任务与结果；`Library.hpp` 暴露 prepare/slice 入口。
- `src/libslicer_api/orca/origin.json`：校准来源固定为 `71c30dd1feb73efa40d824ee1e4be05fce7b0827` 的 `src/slic3r/GUI/Plater.cpp`。这个提交仅是当前校准来源，不是所有功能的统一基准。
- 同一提交的 `src/slic3r/GUI/calib_dlg.cpp` 与 `Tab.cpp`：参数解析、默认值、失焦和相关选项来源。温度表单失焦行为与直接提交的数值契约应分别核对。
- `src/libslicer_api/orca/PlaterCalibration.original.inc`：未编译的原始函数参考；`PlaterCalibration.inc` 是去 GUI 访问后的生产实现。
- `src/libslicer_api/Plater.hpp/.cpp`：所需模型/配置/盘操作上下文；`OrcaCalibrationApi.cpp` 将公开请求和表单协议接到原始能力。
- `tests/libslicer_api/check_plater_source.py`：检查固定来源、原始算法摘要及允许的 GUI 适配；不通过重写来源摘要掩盖额外算法改动。
- `tests/libslicer_api/test_orca_plater.cpp`：比较公开封装与直接原始 Plater 调用的有效模型、配置和可执行 G-code，并检查表单规则。

## 6. 验证与改动审查

先在库层验证输入输出、单位、配置、资源、诊断和相关取消/失败行为；对相同输入比较原始调用与封装调用的有效结果。复用语义要求一致时保持一致，有需求指定的差异则分别明确断言。
来源检查与输出比较各有作用：直接原始调用若与封装共享提取代码，需配合固定来源检查或独立可信基准，避免两条路径同时改错仍彼此相等。
再按需要检查 App 的 Backend/Bridge/界面接线；界面可见或截图成功不能代替库能力正确。
复用现有来源审计与测试工具，只有实际需要时增加相应检查，不为每个小改动建立通用审计框架或完整长模型矩阵。
最终审查新增代码是否确实属于契约、必要适配或需求差异，是否产生平行规则/算法、无关重构或额外全局状态。
