# 多仓临时分支与 MR 回归流程

本文记录本轮讨论最终确认的提交、回归和合并约定。MR 与 GitHub PR 在本文中指同一流程。

**状态：流程设计已审核，workflow 自动门禁尚未实施。** 本文和对应 skill 的提交不表示已部署 workflow、配置分支保护或完成跨平台全量回归。现有 App 手动构建能力见 [CI 文档](ci.md)。

## 1. 本批改动提交在哪里

App、GPlatform、TestAssets 各自使用一个**同名临时分支**。例如三仓都使用 `work/example-change`，但仍分别保存自己的提交历史。

- 本批业务代码、测试资产、文档和 skill 都提交到对应临时分支，不直接提交到 main 或其他长期目标分支。
- 修改涉及 Orca 等子仓库时，也在该仓库使用同名临时分支并提交实际代码。
- PR 的目标是各仓本批明确约定的工作分支，不能擅自把目标设成 main。
- 不为没有实际变更的仓库制造空提交或空 PR。主仓库的子模块引用更新属于实际变更。
- 不修改 `.gitmodules` 的长期 branch 配置来代替提交 gitlink；依赖版本由提交中的准确 SHA 固定。

先完成本地必要验收，本地 commit 按子到父完成：TestAssets／Orca 等子仓库 → App 代码及子仓库引用 → GPlatform 代码及 App 引用。只要求 commit 时，不因子提交尚未推送而阻断父仓本地提交。获得 push 授权后再按同一顺序推送，父仓库推送前确认引用的子提交已经可从远端获取。

提交、push、创建 PR、合并、发布和删除分支是不同操作，按本次授权执行。用户后续明确要求 push 时，以最新指令为准；不因已经允许 push 就自动创建 PR、合并或发布。

## 2. 候选程序与既有回归资产分开

| 角色 | 来源 |
| --- | --- |
| 被测程序 | GPlatform 临时分支候选提交及其锁定的 App、Orca、SDK 等依赖 |
| 本批新增测试／测试修改 | TestAssets 同名临时分支的提交，作为本批待交付内容 |
| macOS 旧功能回归 | 明确选定的既有 macmini 回归脚本、模型及标准提交 |
| Windows 旧功能回归 | 明确选定的既有 Windows 回归脚本、模型及标准提交 |
| 原生切片回归 | 各目标架构选定的既有 catalog 与平台基准提交 |

回归的目的是用候选程序检查以前的功能是否被破坏。本批新增场景做本地必要验证后即可进入 TestAssets 临时分支；**不要求它事先在 macmini／Windows 跑过，也不要求平台分支先接收它，才允许提交或进入本批 MR。**

不得增加“平台回归资产必须包含本次 Test PR”“平台资产必须以本次 Test 提交为祖先”“新增场景目标机器预跑证明”等门槛。后续平台承接、适配新增场景另行处理，不能据此直接把本批测试提交到 main。

既有回归集在本次开始时冻结。不能为了通过而从集合中删掉旧场景、降低比较标准、换成新增场景集合，或自动重录基准。本次运行不隐式 merge、cherry-pick 或写回测试资产。

## 3. MR 回归主入口：4 个对外参数

主入口沿用 GPlatform 的 `run-regression.yml` 职责，补齐现有入口缺少的资产参数透传；不另建一套构建／验收框架。

| 参数 | 意义 | 手动运行 | MR 合并门禁 |
| --- | --- | --- | --- |
| `source_ref` | GPlatform 被测源码的临时分支名或完整 commit SHA | 指定要测试的产品版本 | 由当前 MR 候选提交产生，不任意覆盖 |
| `test_assets_ref` | macOS 既有回归资产的分支名或完整 SHA | 默认 `macmini`，可选择明确的既有版本 | 选定后冻结为准确 SHA |
| `windows_test_assets_ref` | Windows 既有回归资产的分支名或完整 SHA | 默认 `windows`，可选择明确的既有版本 | 选定后冻结为准确 SHA |
| `platform` | `all`、`macos` 或 `windows` | 默认 `all`，单平台用于排查 | 固定 `all`；单平台结果不能满足全量门禁 |

每个 ref 用一个字段表达分支或完整 SHA，不再增加互相冲突的 branch／commit 双字段。分支只在 prepare 阶段解析一次，后续构建、测试和报告均使用冻结 SHA。

产品集成入口中的 App、Orca、SDK 从 GPlatform → App 依赖指针派生，不增加独立覆盖它们的参数。现有独立 App 手动构建入口的 `source_ref`／转发 `app_ref` 仍表示 App 源码，两种入口的源码仓库含义不能混用。

MR 模式固定两平台 Journal 必须执行、`publish_release=false`。这些是策略，不增加给用户绕过门禁的开关。既有手动编译打包的跳过 Journal 开关可以保留，其结果不能冒充 MR 全量通过。

workflow 控制代码版本与被测产品源码版本分别记录。选择 workflow 的执行分支不能代替产品 `source_ref`。

## 4. 执行顺序

1. 本地修改与必要验收完成，向各仓同名临时分支 commit、push，核对依赖引用。
2. 创建并关联本批 PR，写明各自目标分支和实际修改。没有创建 PR 的授权时，仅交付临时分支和提交号。
3. 由 MR 创建／更新事件进入主流程。子 PR 的轻量通知负责让关联组合失效，不在每个仓库重复启动一套长回归。
4. prepare 核对关联 PR、源码及依赖指针，固定 GPlatform、App、Orca、SDK、本批 Test 提交、两平台既有回归资产和各架构原生资产 SHA。
5. 核对 SDK 生产输入和消费来源契约。匹配则复用；不匹配则先通过现有 SDK 更新、交付和 pin 更新流程准备匹配版本。Orca 变化也可能触发更新，不能仅按 ABI 判断，也不无条件重产每批 SDK。
6. 使用正式 presets 配置、构建候选程序及必需测试目标，执行规定的原生测试与既有切片回归。
7. 复用 App 现有流程执行 SDK 消费构建／检查、部署、安装包生成，以及 macmini／Windows 各自的全部既有正式 Journal。被测程序必须来自本次实际构建。
8. 保存逐项结果与证据，汇总后给本批准确候选提交回写合并检查状态。

PR 输入未对齐时，只明确报告未就绪；不能拿旧二进制继续运行。子 PR 更新但父指针尚未更新时，不因每次通知都重复启动长回归。一个最终固定组合只执行一套全量。

## 5. 全量范围与结果

| 检查 | 范围与执行约束 |
| --- | --- |
| 原生测试 | 正式配置中规定的宿主 CTest、Orca core／公开 API 等注册测试，保存实际清单和结果 |
| 既有切片回归 | 标准 48 项与扩展 26 项，逐架构明确 catalog／基准资产 SHA；注册 CTest 与直接比较器选择一种入口，每架构同一套 74 项只跑一次 |
| SDK 消费 | 匹配 SDK 的实际 App 消费构建与现有消费检查 |
| GUI 旧功能回归 | macmini、Windows 各按本次冻结的既有集合执行全部正式 Journal；数量从该集合枚举，不写死为历史数量 |
| 安装包 | 沿用现有生成与产物检查；未实际执行安装就不能声称安装验收通过 |

Journal 全量不等于原生算法全量。Root 原生回归阶段与 App GUI 阶段明确分工，避免重复执行全部 Journal。macOS 已有的同一部署产物打包／回归并行能力继续复用；持有物理机锁时不得等待另一个需要同一把锁的子 workflow。

既有原生资产和 GUI 资产可以使用不同固定 SHA。不得擅自把原生输入改成本批 Test 临时分支，也不要求两个平台资产的无关历史内容完全相同。

只有规定清单全部执行、每项验收通过且必需产物与报告完整，才满足本批合并门槛。失败、取消、空集合、未完成、跳过必需项和 `not_verified` 均不算通过。源码检查、构建、部署、库加载、App 启动、业务检查、安装与实机打印分别报告，不扩大证据结论。

## 6. PR 状态与收尾

- 同一组合的报告约束关联 PR，不为三个仓库重复跑三遍全量。
- 相关 PR head、依赖或本批选定输入变化后，旧组合结果失效；未通过的新 head 不得沿用旧绿色。旧 run／旧 attempt 不能覆盖新组合状态，冲突批次不能互相覆盖同名检查。
- 普通 PR 说明措辞变化不触发长回归；新提交通过轻量通知检查组合，最终输入就绪后再运行。
- 手动 `workflow_dispatch` 的普通 job 状态不能直接当作关联 PR head 的强制检查。落地时需要准确状态回写、失效通知和分支保护配套。
- 跨仓状态写权限仅交给可信控制／结果步骤；执行候选源码的构建任务不持有跨仓写状态凭据。自托管构建保持现有受信维护者范围。
- 失败后继续向原临时分支提交修复；阻止的是合并，不能禁止提交修复。
- 全部通过后，人工最终核对版本并按子到父合并到各 PR 已明确的目标分支。跨仓不承诺原子合并，也不默认部署自动 merge 服务。
- 删除临时分支前，确认父引用的被测子提交在远端合并目标中仍然可达。若 squash／rebase 改变依赖 SHA，正常更新父 pin 并重新验证变化后的组合。
- MR 验证保留安装包、哈希、逐例报告、DB／截图差异和业务输出，不自动发 Release 或刷新基准。

## 7. 当前实现边界

已有能力：App `build-app.yml` 支持 App branch／完整 SHA、macOS 和 Windows 独立测试资产 refs；Root 控制入口已有源码 ref 解析和 App 调度链。复用这些机制。

待实施项包括：主入口两平台资产参数透传、强制 MR 事件和准确状态绑定／失效、关联检查及保护规则、macOS 全量清单检查，以及 Root 旧测试路径迁移。旧原生探针构建器动态生成 CMake 工程，须把现有探针接入维护中的正式 preset 目标，继续复用比较协议和 provenance，不能直接沿用旧 wrapper。

本轮文档和 skill 的落地，不替代这些实现，也不代表已运行一次双平台全量。真正实施和验收时以实际 workflow、固定输入、报告及线上保护配置为准。
