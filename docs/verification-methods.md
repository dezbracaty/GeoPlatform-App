# 验证方式与复用契约

## 固定的六类验证方式

方法按“如何证明结果正确”划分。普通场景只选择方法、填写输入和独立预期，不增加验证方式或专用执行脚本。
注册表唯一实现为 `tools/verification_methods.py`，可用 `python tools/run_acceptance.py --list-methods` 查看。

| ID | 验证对象 | 必需证据与通过条件 | 当前接入情况 |
| --- | --- | --- | --- |
| `state` | 业务状态与配置 | 独立预期与实际状态一致；包含目标对象、配置值、操作前后或撤销重做结果 | `journal-db` 复用正式 `verify.db` 完整序列化比较；需要确定性输入和可信预期 |
| `geometry` | 几何与数值性质 | 尺寸、包围盒、体积、连通性、面数或涂色区域等实际测量符合解析预期和显式容差 | 已有原生几何回归；尚未把真实 App 结果接入共享 Journal 业务验收 |
| `toolpath` | 刀路语义 | 解析最终刀路，核对层高、层数、喷头/材料、换头高度段、打印区及挤出约束等声明要求 | `gcode-job`，目前支持参数化立方体与高度段任务 |
| `artifact` | 文件格式与一致性 | 文件来自本次运行、格式有效，声明内容完整，包内外输出及校验值一致 | `gcode-job` 当前复用双格式打印任务检查；仅有文件或非空不够 |
| `visual` | UI 和渲染外观 | 可信基线、实际图、差异图与容差，固定平台、窗口、DPR、主题等条件 | `journal-screenshot` 复用正式 `verify.screenshot`；当前没有已批准的生产截图基线 |
| `physical` | 设备上的实际打印 | 设备、固件、材料、任务哈希、设备日志、实物测量/照片及复核人，满足明确质量与精度条件 | 尚未接入；软件输出、模拟设备事件或模拟校准观察均不能替代 |

CTest/Python 是测试执行入口，Journal 是真实 App 操作回放入口；它们可以承载不同验证方式。
资产预检、编译成功、程序启动、操作派发、日志和截图采集是执行条件或证据收集，不单独证明业务正确。
一个场景可组合多种方式；同一方式可由不同公共检查器实现，检查器必须复用既有比较规则。

## 方法、检查器与场景的职责

- 方法定义验证对象、证据类型和通过语义，六个 ID 属于架构契约。
- 检查器是共享实现，定义输入格式、支持的参数、独立预期、容差、输出报告及错误行为。
- 场景是数据，声明操作步骤、资产、测试目的、必需方法和检查参数。

新增机型、耗材、尺寸、换头间隔、模型或输入边界，优先改变场景数据。
`P3`、`50mm`、`每三层换头` 不能成为新的验证方式或专用 runner。
当前 `gcode-job` 同时提供 `toolpath` 和 `artifact` 两类证据，预期中的机型、尺寸和高度段均为参数。
它支持的输入范围有限；不能将任意模型假装成已支持的立方体。扩展范围应修改公共检查器契约并增加拒绝错误结果的测试。

仅当既有检查器确实无法表达新的通用比较规则时，才在六类之一注册可复用检查器。
新增第七类方式需要更新本架构、共享注册表、资产 schema 和契约测试；场景文件不能自行注册方法、Python 路径、shell 或命令。

## 场景声明

场景 metadata v2 必须声明至少一个已注册且不重复的方法，例如：

```json
{
  "verification": {
    "requiredMethods": ["toolpath", "artifact"]
  },
  "checks": [
    {
      "id": "print-job",
      "validator": "gcode-job",
      "required": true,
      "artifacts": ["gcode", "package"]
    }
  ]
}
```

此片段省略场景身份、输入和 `expected` 等其他必填数据，完整示例见资产仓库的 P3 场景。
`verify.db` 与 `verify.screenshot` 继续按正式 Journal v2 保存，入口自动识别为共享检查器；不重复保存一份比较逻辑。
截图基线必须位于资产仓库内，其哈希参与运行前后输入一致性检查。基线的独立依据和环境条件仍需维护者审阅，不能采纳当前错误输出消除差异。
`capture.db` 和 `screenshot.capture` 只有采集语义，不会自动生成通过检查。

必需方法来自场景承诺的业务范围。每项验收要求都应能对应到独立预期和检查证据；仅声明方法并不代表已经有足够断言。
只验证导出菜单展开的场景要求 `visual`；真正导出双格式文件的任务才要求 `artifact`。
几何回归任务通常组合 `state` 与 `geometry`，涂色外观还需要 `visual`；校准软件任务通常组合 `state/toolpath/artifact`。
真实打印属于独立场景或独立验证记录，当前软件场景不默认要求 `physical`。

## 预检、执行与最终判定

`--list` 对每个场景同时输出两种信息：

1. `preflight`：资产、路径、哈希和契约是否有效。未知方法或检查器属于 `blocked`。
2. `verificationPlan`：`requiredMethods/checks/missingMethods/readiness`。
   资产齐全但缺少必需检查时为 `missing_checks`，允许诊断回放，不能据此获得业务通过。

执行后 `case_result.json` v2 保存每类必需方法的 `methodResults` 和对应 `checkIds`。
方法只有在覆盖它的必需检查全部通过后才通过；可选检查不能满足必需方法。
缺少方法、断言跳过、断言结果不完整或仅有 Journal 总体 `acceptance=passed`，均不能补出通过。
执行/清理失败或必需检查不符使场景失败；否则所有必需方法通过，场景才通过。

`not_run` 用于尚未执行的步骤/检查；`not_verified` 表示业务证据不足。计划就绪与实际通过是不同维度。
原始 Journal `acceptance` 原样保存，原生测试也保留各自报告，不能将独立 CTest 的几何通过计入当前 Journal 的几何结果。

## 当前迁移范围与后续顺序

80 个场景已根据现有目的逐项声明所需方法，Journal 操作保持原样，没有通过自动录制当前输出来建立预期。
当前 1 个场景具有完整的已声明检查计划，79 个场景缺少至少一类检查；此数值是迁移时的能力盘点，不是运行结果。

后续按公共能力推进：先接入可复用的业务状态/几何检查与可信预期，再补公共刀路与文件检查的参数范围，最后建设受控视觉基线和独立实机记录。
同一批能力一次服务多个场景，之后按场景数据分批执行，不为剩余场景逐个编写验证程序。
